우리두는 "소모임처럼 모이고, 토스처럼 관리하되, 운영 리스크는 시스템으로 통제한다"는 목표로 시작했습니다.

## 3) 신뢰 구축의 핵심: 보증금 락(Deposit Lock) 시스템

### 핵심 메시지
보증금 락은 가입-미납-복구-해제 전 주기를 자동화해 중도 이탈과 금전 사고를 예방하는 장치다.

### 말하기 대본
보증금 락은 4단계로 동작합니다.  
가입 시 락이 설정되고, 미납 시 자동 충당과 권한 제한이 적용되며, 7일 이내 충전 시 즉시 복구됩니다.  
정상 탈퇴 시 락은 해제되어 크레딧으로 환원됩니다.  
핵심은 운영자의 재량이 아니라 규칙 기반 자동 처리라는 점입니다.

## C. 기술 Q&A 10 (기획-구현 차이 대응 포함)

> 형식: `질문` / `짧은 답변` / `근거 문서` / `구현 근거`

### Q1. 왜 기획 문서에는 API 91/92인데 데모는 88인가요?
- 짧은 답변:
  - 기획 문서는 버전별 확장 범위가 함께 포함돼 수치가 변동됐고, 데모 수치는 코드 스캔 기준 구현 완료 엔드포인트 88로 확정했습니다.
- 근거 문서:
  - `docs/01_PLANNING/Product/PRODUCT_AGENDA.md`
  - `docs/02_ENGINEERING/Backend/API_SPECIFICATION_1.0.0.md`
  - `docs/10_Demo/OUTPUT_05_ADDITIONAL_DELIVERABLES.md`
- 구현 근거:
  - `docs/10_Demo/OUTPUT_03_API_DEFINITION_IMPLEMENTED.md` (Total endpoints 88)

### Q2. DB는 32개인가요 33개인가요?
- 짧은 답변:
  - 원문 헤더에는 32가 남아있지만 섹션 단위 집계/코드 추적 결과는 33으로 정리되어 데모에서는 33을 사용합니다.
- 근거 문서:
  - `docs/02_ENGINEERING/Database/DB_Schema_1.0.0.md`

- 구현 근거:
  - `docs/10_Demo/OUTPUT_01_DB_SCHEMA_FROM_DEFINED_DOCS.md` (33/368/58/95)

### Q3. 투표 상태가 IN_PROGRESS인지 PENDING인지 왜 다르게 보이나요?
- 짧은 답변:
  - 기획/구문서의 상태명이 혼재되어 있었고, 구현에서는 PENDING 중심으로 정규화해 상태 전이 일관성을 확보했습니다.

- 짧은 답변:
